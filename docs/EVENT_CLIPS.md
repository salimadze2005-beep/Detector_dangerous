# Видеофрагменты тревожных событий

## Зачем это нужно

При срабатывании тревоги приложение сохраняет короткий видеоконтекст, чтобы оператор мог увидеть не только кадр в момент события, но и несколько секунд до и после него.

Текущие параметры специально выбраны как компромисс между полезностью и памятью:

- 3 секунды до события;
- 3 секунды после события;
- 5 кадров/с;
- максимум 960×540;
- кольцевой буфер хранит JPEG-сжатые кадры с качеством 70;
- итоговый файл — MP4 (`video/mp4`, codec `mp4v`).

Сырые кадры камеры в памяти не накапливаются. В оперативной памяти находится только короткая JPEG-история, поэтому расход RAM ограничен и растёт примерно линейно с количеством активных камер.

## Какие события записываются

Клип создаётся для:

- `GUNSHOT_DETECTED` → каталог `gunshot`;
- `KEYWORD_DETECTED` → каталог `keyword`;
- `FALL_DETECTED` → каталог `fall`.

Для падения записывается камера из `camera_id`. Для аудиособытий сначала используются камеры, привязанные к микрофону через `camera_ids`. Если явной привязки нет, сохраняются активные камеры.

Разделение по типам событий сделано только на уровне архива. Механизм записи, формат MP4 и `event.json` одинаковы для всех трёх типов — это проще поддерживать и позволяет позже использовать единый REST-контракт.

## Логика тревоги падения

Устойчивая поза `Лежит` запускает таймер подтверждения даже если камера не успела увидеть момент перехода из положения стоя или резкое движение вниз.

На аннотированном кадре во время подтверждения показывается счётчик вида:

```text
Состояние: Лежит: 2.4/5.0с
```

После достижения `fall_duration_sec` (по умолчанию 5 секунд) формируется `FALL_DETECTED`.

Если до лежания камера видела человека стоящим и/или зафиксировала быстрое движение вниз, эта информация сохраняется как дополнительное подтверждение в metadata (`seen_upright`, `motion_confirmed`, `vertical_speed`), но больше не является обязательным условием запуска тревоги.

Это означает, что человек, который уже лежал при появлении в кадре, также вызовет тревогу после устойчивых 5 секунд в позе `Лежит`.

## Где хранятся файлы

Файлы сохраняются локально и не попадают в Git:

```text
data/event_clips/
    fall/YYYY/MM/<event_id>/
        event.json
        <camera_id>.mp4
    gunshot/YYYY/MM/<event_id>/
        event.json
        <camera_id>.mp4
    keyword/YYYY/MM/<event_id>/
        event.json
        <camera_id>.mp4
```

Один каталог соответствует одному `event_id` из `EventBus`.

## `event.json`

Манифест нужен для аудита и дальнейшей REST-интеграции. Он содержит:

- `schema_version`;
- `category` (`fall`, `gunshot` или `keyword`);
- полный сериализованный объект события;
- длительность контекста до/после события;
- целевой FPS;
- список клипов по камерам;
- источник камеры;
- имя и относительный путь файла;
- MIME-тип;
- codec;
- число кадров;
- фактическую длительность;
- смещение первого и последнего сохранённого кадра относительно события;
- размер файла в байтах.

Пример:

```json
{
  "schema_version": 1,
  "category": "gunshot",
  "event": {
    "id": "abc123",
    "type": "GUNSHOT_DETECTED",
    "confidence": 0.82,
    "source": "audio.gunshot.17",
    "severity": "critical",
    "timestamp": "2026-08-17T10:00:00+00:00",
    "metadata": {}
  },
  "evidence": {
    "format": "mp4",
    "annotated_video": true,
    "pre_event_sec": 3.0,
    "post_event_sec": 3.0,
    "target_fps": 5.0,
    "clips": [
      {
        "camera_id": "camera-123",
        "file": "camera-123.mp4",
        "media_type": "video/mp4"
      }
    ]
  }
}
```

## Что отправлять по REST

Текущий REST-контракт приложения **не меняется** этой задачей. Клип сначала сохраняется локально, чтобы формат передачи можно было согласовать отдельно.

Практичный вариант для внешнего API — `multipart/form-data`:

- `description`: текст тревоги;
- `event_id`: идентификатор события;
- `event_type`: тип события;
- `occurred_at`: ISO-8601 время;
- `manifest`: `event.json` (`application/json`);
- `clip`: MP4 (`video/mp4`).

Если камер несколько, API может принимать несколько полей `clip` либо отдельные `clip_<camera_id>`.

MP4 предпочтительнее GIF: он существенно компактнее для 6-секундного фрагмента, лучше сохраняет детали и подходит для стандартных видеоплееров/архивов.

## Что проверить перед merge в `main`

1. Запустить систему с веб-камерой или RTSP.
2. Дать видеопотоку поработать минимум 3–5 секунд, чтобы заполнился pre-event buffer.
3. Проверить падение: человек должен устойчиво отображаться как `Лежит`, счётчик должен дойти до 5 секунд, после чего должна появиться тревога.
4. Подождать минимум 3 секунды после тревоги.
5. Проверить соответствующий каталог `data/event_clips/<category>/YYYY/MM/<event_id>/`.
6. Открыть MP4 и убедиться, что в нём есть кадры до события и после него.
7. Проверить `event.json` и соответствие `event_id` тревоге.
8. Повторить для выстрела и ключевого слова.
9. При RTSP временно разорвать поток и убедиться, что отсутствие клипа не ломает саму тревогу.
